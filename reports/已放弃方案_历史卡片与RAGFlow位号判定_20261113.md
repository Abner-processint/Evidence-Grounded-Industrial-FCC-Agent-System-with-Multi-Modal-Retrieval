## 方案一：多轮历史卡片

### 原理

- **要解决的问题**：多轮对话里，第 3 轮会改选别的表。11-11 盘点 42 个后续轮，有 3 个是这样：一中回流前两轮按 FRC3209，第 3 轮变成单取 FRC3208。
- **原因**：表是「定义因子」那一步选的，它看不到前几轮用的是哪块表，只能从调研资料「一中量以FRC3208为准」重新读，而这句话被读成了整个一中回流。
- **现有的前轮信息传递方式都靠不住**：
  - 按关键词挑问题卡 / 事实卡，64 轮里命中 0 次；
  - 前几轮回答各只传前 600 字，前轮关键取值有 39% 落在 600 字以后；
  - 写回答一步只拿到上一轮全文。
- **设想**：每轮结束时，由代码从结构化结果生成一张「卡片」，记下这一轮实际用了哪些量、哪些位号、选法依据和取数时段。下一轮把卡片交给定义因子那一步，让它与前轮保持一致。卡片由代码生成，不经过模型转述，也不受截断影响。

### 实现

- **离线原型**（`build_cards.py`，三版）：

  | 版本 | 卡片内容 | 暴露的问题 |
  |---|---|---|
  | v1 | 带均值 | 模型把卡上的均值当成本轮实测，不再列流量因子；回炼比被挂上了输入位号 |
  | v2 | 不带数值 | 第 1 轮的位号字段是候选全集，新鲜进料被并成 10 块表 |
  | v3 | 只记计算实际用过的输入、依据是否来自知识库；多块表又没说相加的标「未定」 | 见下 |

- **测试副本**（`r1112`，改 3 个节点）：
  - Capture context 读回卡片；
  - Save Conversation State 每轮由代码记一张卡，最多 8 张，不记数值；
  - Coverage Check LLM 插入前几轮卡片和卡片规则。

  规则改过三版：
  - V3 是第一版；
  - V4 加「卡片不顶替装置模型查询」；
  - V5 加「卡片列了位号也照查」。

  最后把规则挪进用户消息、紧挨卡片放，使首轮提示词与主线逐字一致。

### 测试结果

- **离线重放**（v3，第 3 轮定义因子，14 组 × 3 遍）：

  | 组 | 结果 |
  |---|---|
  | 换表 3 组 | 修好 2 组（2/3、3/3）；1 组没修好：第 1 轮自己就把 FRC3208 叫成一中回流流量，卡片照实沿用 |
  | 一中对照 5 组 | 15/15 与前轮一致 |
  | 回炼比 4 组 | 新鲜进料 12/12 用三块表 |
  | 稀相压降 2 组 | 卡片为空，不变 |

- **副本实跑**（15 个多轮会话、8 道单题）：
  - 一中回流 6 组第 3 轮都按前轮定义取流量，不再单取 FRC3208；
  - 回炼比 3 组都是 0.01604；
  - 单题 7/8 与主线一致；
  - **稀相压降第 3 轮变坏**：6 个会话 0 个算对（4 个没算、2 个算成 1018.39 kPa），同时间主线 2/2 正确。

  原因：卡片列了 DR3110，模型就更少去查它的取压口数据。同一份提示词统计请求查 DR3110 的次数：

  | 提示词 | 无卡片 | 加卡片 |
  |---|---|---|
  | 主线 | 8/8 | 5/8 |
  | 副本 | 5/8 | V4 0/8、V5 2/8 |

  规则能压低，但压不干净。
- **修了根子后再测**（11-12）：取压口数据改由代码去取（第 17、18 项），在此基础上加卡片：
  - 取压口事实到位 3/3；
  - 压降 1.018 一次、1018.39 两次（毫米没换米，原有毛病，第 19 项已修）；
  - 一中 2/2 一致；
  - **回炼比 1/2 错（0.0127）**：卡片让定义因子把新鲜进料定成「三表相加」的一个因子，计算那一步又写了一遍三表相加，绑定把和当成一路，另配了两块喷嘴支路表，分母变成 331 t/h。

### 结论：放弃

1. 卡片只修了「第 3 轮换表」这一类，盘点里 42 个后续轮只有 3 个。这一类的根子是厂里没确认「一中回流流量看哪块表」，问题稿已写好待发；厂里确认后写进知识库，就不再需要卡片。
2. 卡片保证前后一致，不保证选对：前轮选错时会原样沿用。
3. 卡片改变了定义因子一步的行为，带来两种副作用：
   - 少查装置模型数据：根子已由代码取数修掉；
   - 改变因子的拆法，导致计算绑定配错：未修。

   每多一种消费卡片的步骤，就要再排查一遍这类副作用。
4. 卡片不带数值，解决不了「第 3 轮直接引用第 1 轮数值」这类问题；盘点里也没有一次不一致是数值被截掉造成的。
5. 副本已恢复为不含卡片的版本（3dcb37e0 = 主线内容）。卡片代码只留在 `n8n_project/r1112/`，不再维护。

**仍然存在的缺口**：三轮对话第 3 轮的稀相压降，DR3110 只在第 1 轮读过，第 3 轮代码取不到它的仪表数据，现在没有方案。

## 方案二：RAGFlow 上下文辅助判定位号

### 原理

- **要解决的问题**：实时库 2843 个位号里有 1811 个（64%）没有描述，而找位号的解析服务靠描述匹配，这批位号基本找不到。
- **9 月已有的三处机制**（仍在主线）：
  - 按文档提升候选位号（DOCUMENT_BOUND_TAG_PROMOTION_V7）；
  - 按位号补查身份（TAG_IDENTITY_PROBE_V7）；
  - 位号资料检索（TAG_DOCUMENT_RETRIEVAL_V7）。

  本月 83 次执行里：按文档提升 0 次；身份补查 6 次，其中 5 次查的位号与问题无关；没有描述的候选 520 个，选中 0 个。
- **原因**：
  - 只认「名称(位号)」括号写法，而文档里位号多写在表格里；
  - 只在本轮碰巧检索到的文档里找：没有描述的候选，111/114 个根本不在本轮文档里；
  - 只能确认已有的候选；
  - 名称对不对得上，靠字面重合判断。
- **设想**：按候选位号专门去 RAGFlow 检索，取它在文档里的上下文（所在表格行、相邻位号），交给模型判断「哪个位号是这个量」，不再用括号规则和字面重合。

### 实现（离线试验，工作流未改）

- 在 n8n 上建临时检索小工作流，用与主线相同的 RAGFlow 地址、密钥和数据集，测完删除，前后建删两次。
- **测试集**：26 个量，含 8 个本来就没有位号的；标准答案人工判定。
- **两步**：
  1. 按量名检索，从片段里取「相关位号」当候选；
  2. 每个候选按「位号.PV」再查一次，取上下文。
- **判定对照**：与线上同一模型，比较「只给画面表描述」和「描述 + 文档上下文」。为单独测判定，标准答案位号人为放进了候选。

### 测试结果

- **按量名检索找候选**：标准答案只召回约 6/21。片段里混着设备号和管径；一再稀相密度取到的是别的再生器的密度表；教科书和月报片段里没有位号。
- **第一次（用全部来源的上下文）**：对 33/52，不如只给描述的 36/52。
  - 规程操作步骤把反应压力带成分馏塔顶压力控制 PRC3201B + C；
  - 正确位号没有文档时，模型偏向有文档的干扰位号（反飞动阀）。
- **重测（只用定义类来源：报警位号表、DCS 控制点统计表、仪表信息表、调研问题、工艺卡片）**：

  | 条件 | 对（共 78 次） |
  |---|---|
  | 只给描述 | 49 |
  | 加定义类上下文，查不到条目的写明「不代表不对」 | 51（把 TRC3201 算作可接受则 54） |
  | 加定义类上下文，不写这句 | 46 |

  - 变好的：集中在「几块表该相加还是互为备选」，如新鲜进料计算点的组成、两器差压的冗余表；
  - 补不上的：设备别名，例如不知道 T3203 就是溶剂再生塔。
- **代价**：
  - 单次检索 7–39 秒；
  - 只认「位号.PV」写法，裸位号查不回；
  - 并发高时 RAGFlow 会悄悄返回空结果：一批 90 条全部 0 段，按每批 4 条重查全部有结果。

### 结论：放弃

1. 找候选这一步召回不到三成，每轮按量名检索找相关位号不可行。
2. 判定这一步，最好的条件也只比只给描述多 2–5 次对，接近波动范围；而且这是在标准答案已放进候选、只测判定的条件下得到的。真实使用时，候选本身就找不全。
3. 每轮检索的代价高：每个量要多查若干次，每次 7–39 秒，文档检索本来已是每题耗时最大的一块；并发一高还会悄悄丢结果。
4. 有用的信息（位号的名称、单位、量程、冗余表、计算点组成）都在几张固定的定义类表格里，不需要每轮检索。

**保留下来的发现**

- 定义类资料里有与画面表矛盾的装置事实，应并列给出，并请厂里确认。例：调研问题写「TRC3201为一中抽出温度」，画面表里它叫「分馏轻柴油抽出温度」。
- 设备别名缺口（如 T3203 = 溶剂再生塔）要靠同义词库补。
- RAGFlow 并发高时会悄悄返回空结果。线上分组检索的并发是 3，有没有因此丢结果尚未查。
- 如果以后还要补位号描述，方向是离线把这几张定义类表格整理成「位号 → 名称 / 单位 / 量程 / 冗余表 / 计算点组成」对照表，审核后补进位号描述或同义词库，而不是每轮检索。

**主线现状**：9 月那三处机制仍在主线上，按上面的统计基本不起作用，但也没有坏处。本次没有删除，是否删除另定。
