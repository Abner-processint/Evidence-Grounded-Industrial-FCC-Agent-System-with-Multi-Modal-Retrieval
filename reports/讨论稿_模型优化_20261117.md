# 讨论稿：FCC 装置问答智能体下一步怎么优化（2026-11-17）

请你作为评审，帮我们判断下一步优化的方向和优先级。下面是背景、现状数据、已经试过的做法，最后是想请你回答的问题。

## 一、系统是什么

- 一家炼厂催化裂化（FCC）装置的问答智能体，搭在 n8n 工作流上，约 200 个节点。
- 主力模型是 DeepSeek（经 API 调用，温度 0）。各步骤都用同一个模型：拆题、规划、选位号、定义计算量、写回答、核对、改稿。
- 数据源：
  - 时序库（MongoDB，逐分钟读数，约 2800 个位号，其中 64% 没有中文描述）；
  - LIMS 库（`d_LIMS`，目前很少用）；
  - 文档检索（RAGFlow，6 个数据集：操作规程、技术月报 2022–2026、技术问答等通识教材、事故分析、表格数据、英文书）；
  - 装置模型库（设备与仪表的静态数据：标高、取压口等）；
  - 小型装置知识库（4 条公司确认的口径，如新鲜进料 = 三块表之和）。
- 流程大致是：拆题 → 规划 → 取数与检索 → 自查补查 → 计算量由代码算 → 写首稿 → 缺失核对 → 核对 → 改稿 → 输出。

## 二、验收要求

- **问答成功率**：100 题，专家盲审，10 分制（准确 5、完整 3、清晰实用 2），7 分及以上算成功，门槛 80–85%。
- **出处可验证率**：按「关键陈述」计数，出处须真实且直接包含所述内容，门槛 85–90%。
- **公司另加**：
  - 第一轮准确率 ≥85%；
  - 经用户确认或纠正后 ≥95%；
  - 回答之间可以不说，但不能有矛盾。「一次说没有、另一次给出」也算矛盾，所以要求：要说没有就不说。
- **公司题库样例**（20 题）：每题都有逐项评分细则，大量分数要求本装置具体数字，例如 2026 年 6 月月报里的原料性质和收率、2024 年标定报告里的主风机静叶角度；另有一项「说明本题不需要调用实时库或 LIMS 的原因」单独给分。

## 三、现状数据（内部预验收，模型自评，偏松）

- 34 题（公司旧版 20 题 + 我方回归 14 题），每题 2 次独立会话：
  - **10 分制自评**：第一次回答 32/34 达到 7 分。这是答题模型给自己打分，偏松。
  - **按要点逐条判**：公司 20 题答全 66%，本装置层最弱。
  - **出处有效率**：89–96%（按回答实际引用的证据核对，代码复核数字 95% 在证据里）。
  - **两次回答之间互相矛盾**：约 19/34 题，**离要求最远**。
- **矛盾的成因**（逐条把两边的说法拿回各自的证据里找）：
  1. **资料本身有多个值，两次各取一个**（约 5 题）：两次的证据里两个值都在。例如同一个位号的报警值，DCS 控制点统计表和报警位号表给的不一样。
  2. **资料里有，一次却说没有**（约 5 题）：是写回答这一步的问题。
  3. **两次检索到的资料不同**（约 5 题）：检索词由模型生成，每次不一样。
  4. **资料相同，推理和判断不同**（约 6 题）：例如冷回流对塔顶温度的作用方向两次相反。
- **资料缺口**：
  - 题库 20 题全部引用《2024 年标定报告》，检索库里没有；
  - 另有两本通识书没有，一本解析失败；
  - 物料平衡表、停工统计等表格解析失败。
- **其他已知问题**：
  - 温度 0 下 DeepSeek 结果仍不确定；
  - 每题耗时 2–5 分钟，文档检索占最大一块；
  - RAGFlow 并发高时会悄悄返回空结果。

## 四、已经试过的做法

| 做法 | 结果 |
|---|---|
| 改成由代码处理：计算要用的仪表数据由代码去取，单位由代码换算（毫米 → 米） | 有效，已上线。试验台上计算一步正确率 38/68 → 63/68 |
| 最后加一步「不说没有」改写：模型给出逐字查找替换，代码只改正文 | 离线：正文里断言「没有」的句子 243 → 67；没有数值被删。已在测试副本上，正在量 |
| 「同一个量资料里有多个值」由模型核对、并列写出 | 离线查准率约 87%，但召回不稳定：同一份输入两次结果不同，会引入新的波动 |
| 多轮对话加「历史卡片」，由代码记下前轮用过的位号 | 修好了第 3 轮换表的问题，但模型因此少查数据，另有分母配错；放弃 |
| 用 RAGFlow 检索到的上下文辅助判定位号 | 全部来源：33/52，不如只给描述 36/52；只用定义类来源：51/78 对 49/78，差距在波动范围内；放弃 |
| 规划一步从推理模型换成默认模型 | 每题快 35 秒，结果不变 |

**团队的原则**：防错尽量靠流程位置、结构化数据和代码计算，不靠在回答文字上做正则或词表匹配；同一个量有多个取值时，全部列出由用户选，系统不替用户择一。

## 五、想请你回答的问题

1. **前后不矛盾**：在模型不确定、检索结果不确定的前提下，怎样让「同一个问题、不同会话」的事实陈述一致？我们在考虑：
   - (a) 把检索计划和查询词按问题固定或缓存；
   - (b) 把定义类表格（报警位号表、DCS 控制点统计表、工艺卡片）离线整理成静态对照表，回答提到哪个位号就由代码附上该位号的全部取值；
   - (c) 建一个跨会话的「已陈述事实库」，新回答先和它核对。

   哪个性价比最高？有没有更好的办法？
2. **第一轮准确率 ≥85%**：照公司题库的样子，评分重在本装置具体数字和口径说明。缺资料补齐之后，提高得分最有效的是改检索（召回、按月报定位）、改写回答（按三层结构、主动写数据口径），还是别的？
3. **换模型还是不换**：哪些问题换一个更强的模型（例如 GPT 6.2 Astra 或 Claude）就能明显改善？哪些和模型无关？有没有必要做一次同输入换模型的对照，怎么设计最省？
4. **后训练**：在只有几十到几百道带评分细则的题、数据不能外传的条件下，用本地开源模型做监督微调或强化学习，有没有可行的切入点？例如只训「选位号」「写计算式」这类能自动判对错的单步。
5. **评估**：现在打分用的是同一个 DeepSeek 自评，偏松。在专家打分之前，怎样做一个更可信的自动评分，比如用不同模型交叉评分、逐项细则、和少量专家打分校准？
